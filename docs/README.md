# 合同智能审查平台 · 项目知识库

> [!important] 这个知识库的定位
> 这不是一份"写给客户"的项目文档，而是一份**写给面试官**的工程档案。
> 每一份笔记都要能回答同一个问题：「你做这个项目时，做了什么判断，为什么这么判断？」

## 甲方是谁

沿用 [AI-vibe-coding工作流](reference/AI-vibe-coding工作流.docx) 的角色分工，只把"客户"换成"面试官"：

| 原始工作流里的角色 | 本项目里的等价角色 |
| --- | --- |
| 客户 / 业务方 | 面试官 + 你自己（用简历筛选标准当验收标准） |
| 真实法院业务痛点 | 企业法务人工审合同的低效环节 |
| 真实 Chrome 验收 | **本机 Windows 服务（MySQL80 + Redis）+ 一键启动** + 可复现的演示脚本<br>⚠️ 原计划 `docker compose up`，因本机未装 Docker 改为直连本机服务（变更 C-11）|
| 业务结果由我判断 | "这段代码我能不能在 3 分钟内讲明白" 由我判断 |

## 使用顺序

1. 先读 [00-项目索引](00-project-index.md)：目标、当前阶段、新会话必读顺序。
2. 读 [01-需求与范围确认](01-requirements-and-scope.md)：做什么、不做什么、怎么验收。
3. 读 [02-系统架构](02-architecture.md)：模块边界、数据流、技术选型与理由。
4. 开发前复制 [03-模块文档模板](03-module-template.md)，按模块名存为 `modules/<module>.md`。
5. 从 [04-任务与验收清单](04-tasks-and-acceptance.md) 只领**一个**任务。
6. 每个任务开工前复制 [05-单任务卡](05-task-card-tdd.md)，先让测试描述预期行为。
7. 开新会话时，用 [06-AI启动提示词](06-ai-session-prompts.md) 里的模板。
8. 范围变了记 [07-变更与交付确认](07-change-and-delivery.md)。

> [!tip] 秋招专用
> [08-秋招面试与验收脚本](08-interview-and-demo-script.md) 是这个知识库和通用模板最大的区别：
> 它把每个模块的**技术决策**反向映射成**面试问答**，并给出 3 分钟演示脚本。

## 笔记保存原则（沿用原模板，未放宽容忍度）

| 信息类型 | 存放位置 |
| --- | --- |
| 代码事实 | 代码、测试、`docs/modules/` 与 `docs/tasks/`（**本仓库没有 `docs/specs/`**）|
| 稳定架构与设计决策 | 本知识库的模块笔记 / 架构笔记 |
| 长期待办 | [04-任务与验收清单](04-tasks-and-acceptance.md) |
| 临时日志、PID、终端输出、调试截图 | 当前任务卡，任务关闭前清理 |
| 大模型 API Key、数据库密码、真实合同原文、真实个人信息 | **不得进入 Git、不得进入本知识库** |

## 与原通用模板的差异（以及为什么）

| 原模板做法 | 本项目调整 | 原因 |
| --- | --- | --- |
| 全面 TDD，一切先写失败测试 | 分两层：**核心业务逻辑（规则引擎、要素抽取、状态机）严格 TDD**；脚手架、配置、纯展示用集成测试或手工验收 | 秋招项目的瓶颈是"深度"和时间，不是覆盖率数字。见 [04](04-tasks-and-acceptance.md#测试策略分层) |
| 突出"客户确认" | 突出"面试官会怎么追问" | 甲方的验收方式变了 |
| 交付物 = 给客户能用 | 交付物 = 能跑 + 能讲 + 能改 | 见 [07](07-change-and-delivery.md#交付清单) |
| 不提简历 | 增加 [08](08-interview-and-demo-script.md) | 这是本项目的最终目的 |
