# 【T-编号】 【任务名称】

> [!tip] 使用方式
> 每领一个任务复制一次本文件，存为 `docs/tasks/T-0XX-<slug>.md`。
> 任务验收后**只回写长期结论**到模块笔记，本卡不长期保留。

## 任务边界

- 所属模块：【链接到 [03-模块文档模板](03-module-template.md) 实例化的模块笔记】
- 对应需求/验收：F-编号 / A-编号
- 目标行为：完成后，用户或系统会有什么**可观察**变化
- 本任务不做：明确排除的功能、重构或顺手修改
- 前置依赖：已完成任务、接口，或「无」
- 涉及的不变式：I-01~I-06 中的哪几条

> [!question] 开始前检查
> 如果目标行为、输入输出、验收方式或依赖任一项不明确，先回到需求/模块文档补充，**而不是让 AI 猜测实现方案**。
> 规格不存在，不动工；规格有歧义，暂停实现。

## 验收示例

### 正常路径

- 给定：前置状态或输入
- 当：操作/事件
- 则：预期可观察结果

### 异常或边界路径

- 给定：前置状态或输入
- 当：操作/事件
- 则：预期错误码、提示或人工处理方式

### 明确不该发生的事

- 【明确写出"不能出现的行为"，例如：不得用默认值兜底、不得落库、不得静默重试】

## TDD 记录

### 1. 失败测试（RED）

- 测试文件/名称：`src/test/java/.../【Class】Test.java#【method】`
- 它要描述的行为：一句话
- 首次失败原因：尚未实现 / 当前行为不符
- 首次运行输出摘要：【贴关键行，不要贴全文；不长期保留】

### 2. 最小实现（GREEN）

- 拟修改文件：【路径】
- 最小改动说明：只说明满足本任务的改动
- 不新增的复杂度：例如暂不抽象、暂不重试；原因
  > 回答 Lean Mode 三问：这个失败真的发生过吗？发生后用户受什么影响？不写这段代码的代价是什么？

### 3. 必要整理（REFACTOR）

- 整理内容与理由：（若无需整理写「无」）

### 4. 验证结果

| 验证项 | 结果 | 证据 |
| --- | --- | --- |
| 新增/修改测试 | 通过/失败 | 测试名称或命令 |
| 受影响的单元测试 | 通过/失败 | 命令 |
| 集成测试 | 通过/不适用 | 命令 |
| 手工验收（若需要） | 通过/不适用 | 简短操作与结果 |
| 全量回归（仅最后跑一次） | 通过/不适用 | 命令 |

- 需要回写的长期事实：要更新的模块/架构/Todo；若无填「无」
