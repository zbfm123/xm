# 合同智能审查平台 · 需求与范围确认

> [!important] 开发前置条件
> 本文档的「目标、范围、验收标准、明确不做」四项必须先确认。任何一项含糊时，先列为待确认，暂不开始相关实现。

## 0. 选题理由

> [!question] 为什么是"合同智能审查"
> 因为 [AI-vibe-coding工作流](reference/AI-vibe-coding工作流.docx) 里的每一条业务红线，都能在 Java 后端找到对应的工程落点：

| 原工作流红线 | 本项目的落点 |
| --- | --- |
| 未知状态必须进入 UNKNOWN / 待人工 | 要素抽取失败 → `EXTRACT_UNKNOWN` → 生成人工复核任务，绝不猜 |
| 选择器变化必须报告 SELECTOR_CHANGED | 大模型返回结构不符合约定 schema → `SCHEMA_INVALID` 显式失败，不吞成默认值 |
| 登录或 OCR 失败最多重试一次 | AI 调用超时/限流最多重试 1 次，之后降级为人工，不做无限重试 |
| 批量任务必须保持串行、节流和命令归属 | 批量审查任务串行 + 令牌桶限流 + 任务归属与幂等键 |
| API 与 DOM 无法互相证明时不得落库 | **AI 结论与原文证据无法对齐时不得写入正式结论**（本项目最重要的一条） |

这条映射关系本身就是面试可讲的内容：**你不是在"用 AI 做功能"，你是在给 AI 的输出做工程约束。**

## 1. 背景与目标

### 要解决的问题

企业法务审一份合同，主要时间花在四件重复劳动上：

1. 通读全文，并在附件里核对甲乙方名称、金额、期限是否一致；
2. 人工翻检"必备条款是否缺失"（争议解决、违约责任、保密、付款节点等）；
3. 凭经验定位风险表述（无限责任、单方解除、自动续约、付款条件不明）；
4. 把结论写进 Word 或邮件，过程无留痕，换个人无法复现判断依据。

### 本次交付的期限约束

> [!warning] 这是冲刺版需求，不是完整版
> - 期限：**国庆结束前（10/7）**，实际可投入约 5 天。
> - 目的：秋招投递前的可演示作品，**优先保证「能讲」，其次才是「功能全」**。
> - 因此 [04-任务与验收清单](04-tasks-and-acceptance.md) 只保留 22 个 P0 任务，
>   统计看板、批量审查、报告导出全部推迟（见 [07](07-change-and-delivery.md#范围变更记录)）。
> - 剩余交付压力由「砍范围」承担，**不由「降质量」承担**——核心的三项（证据对齐、降级路径、审计只追加）绝不缩水。

### 本项目目标

交付后，用法务账号能够完成这条可观察的闭环：

> 上传一份 PDF/DOCX 合同 → 系统提取出结构化要素 → 规则校验标出确定性问题 → AI 标出风险条款并给出原文引用 → 我能逐条"采信 / 驳回" → 打开一份带审查痕迹的报告页（浏览器打印即可）。

> [!note] 与常规版的差异
> 原句结尾是"导出一份报告文件"。5 天期限内**导出功能降级为浏览器打印**，不生成 PDF/Word。
> 这是明确的取舍，不是遗漏——面试时应当主动说明（见 [08](08-interview-and-demo-script.md)）。

### 成功标准

- S-01 `docker compose up` 后 5 分钟内可完成上述闭环，无需手工改配置。
- S-02 规则校验的判定依据**完全可复现**：同样输入必然同样输出，有单元测试覆盖。
- S-03 AI 产出的每一条风险结论都带**原文片段引用 + 字符区间 + 置信度**；无法定位到原文的结论不得出现在报告里。
- S-04 核心业务代码有我能在面试中逐行解释的设计决策记录（对应 [08](08-interview-and-demo-script.md)）。
- **S-05（本次新增）** 在 10/7 前完成 [04](04-tasks-and-acceptance.md) 中全部 22 个 P0 任务，并有一次完整的 3 分钟演示演练记录。

## 4. 核心使用流程

### 场景：法务审查一份采购合同

1. 法务登录，进入合同列表，点击上传。
2. 上传 `采购合同.pdf`；系统校验格式与大小，存对象存储，提取文本并归一化（去页眉页脚、统一空白）。
3. 法务点击"提取要素"；系统走抽取通道得到结构化要素，每个字段带 `charStart/charEnd` 原文位置。
4. 法务点击"规则校验"；规则引擎用要素做确定性判断（金额大小写不一致、签署日晚于生效日、缺失争议解决条款等）。
5. 法务点击"AI 审查"；AI 模块逐段识别风险条款，产出候选条目与置信度。
6. 系统校验每条 AI 结论的原文区间能否在文本中命中；命中的入库为候选，未命中的标记 `EVIDENCE_MISMATCH` 转人工。
7. 法务逐条采信/驳回，填理由；低置信度条目必须由主管复核后才能进入报告。
8. 法务导出报告，报告里同时列出规则结论、AI 建议和人工意见，三者可区分。

### 异常流程

| 情况 | 用户会看到什么 | 系统如何处理 | 是否需要人工介入 |
| --- | --- | --- | --- |
| 上传了加密 PDF | "文件已加密，无法解析" | 解析失败，合同状态置 `PARSE_FAILED`，不产生任何要素 | 是 |
| 要素抽取置信度低于阈值 | "以下字段需人工确认" | 字段标记 `LOW_CONFIDENCE`，不写入确认状态 | 是 |
| 大模型超时/限流 | "AI 审查暂时不可用，可稍后重试" | 最多重试 1 次，仍失败则任务标记 `AI_UNAVAILABLE`，规则结论不受影响 | 是 |
| 大模型返回结构与约定 schema 不符 | "AI 返回格式异常" | 显式报 `SCHEMA_INVALID`，丢弃该次输出，**不用默认值填充** | 是 |
| AI 给的风险条款原文定位不上 | "该条证据无法定位，已转人工" | 该条标记 `EVIDENCE_MISMATCH`，不进报告正文 | 是 |
| 同一合同重复提交审查 | 提示"已有进行中任务" | 幂等键去重，直接返回已有任务 | 否 |

## 6. 非功能要求

- 使用环境：Chrome 现代版本；后端 Linux/macOS/Windows 均可跑；本地用 Docker Compose。
- 性能要求：单份 30 页合同，规则校验在 3 秒内返回；AI 审查为异步任务，提交后 60 秒内可见首条结果。
- 安全与隐私：租户级数据隔离（每个查询强制带 `tenantId`）；密码 BCrypt；API Key 仅环境变量；日志脱敏（不打合同全文、不打 token）。
- 成本控制：AI 调用必须有单合同段落数上限、单日调用预算上限、结果缓存（同文本哈希不重复调用）。
- 稳定性：AI 通道不可用时，规则审查与人工流程必须仍可正常使用（**降级而不是整体失败**）。
- 交付形态：源码 + `docker-compose.yml` + README（含启动与演示步骤）+ 本知识库。
